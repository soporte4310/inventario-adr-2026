------------------------------------------------------------------------
1. CONTEXTO
------------------------------------------------------------------------

INACAP necesita automatizar la revision mensual que hacen los practicantes
sobre proyectores (en salas) e impresoras (en oficinas). Hoy esa revision
es manual y no queda historial digital: no hay forma de saber que se
reviso, cuando, quien lo hizo, ni de adjuntar evidencia de una novedad
(foto/video + comentario). El README del proyecto ya anticipaba este
modulo como "Mantenimiento Preventivo" en su hoja de ruta.

Se construira como una APP NUEVA de Django (mantencion) dentro del mismo
proyecto/repositorio, reutilizando el login, los grupos de permisos y el
modelo Activo/Ubicacion ya existentes en inventario, para no duplicar
datos ni interferir con esa app.

------------------------------------------------------------------------
2. DECISIONES YA CONFIRMADAS CON EL EQUIPO
------------------------------------------------------------------------

- Reutilizar Edificio / Piso / Ubicacion de inventario (no se duplica la
  jerarquia de ubicaciones).
- Videos de evidencia: SIN transcodificar en servidor (se valida y se
  sube tal cual). Las FOTOS si se procesan con el pipeline Pillow ya
  existente (resize + conversion a JPEG).
- El listado mensual se genera con un COMANDO PROGRAMADO (mismo patron
  que el reporte semanal de inventario), no de forma perezosa ni 100%
  calculada en vivo.
- Nombre tecnico de la app: mantencion.
- Layout / navbar / modo oscuro: INDEPENDIENTE del templates/base.html
  compartido con el resto del sitio (no se toca inventario/adr).
- Grupos que pueden revisar (marcar OK / subir evidencia): ADR, Alumno
  en Practica, Auxiliar Operador ADR, Operador ADR.
- Solo el grupo ADR administra el roster de equipos y la estructura
  Edificio/Piso/Ubicacion.
- Reporte final: solo boton manual "Enviar reporte" en la version 1
  (sin cron/envio automatico adicional por ahora).
- El middleware ForcePasswordChangeMiddleware NO se toca (ya funciona
  hoy via CustomLoginView, ver punto 3).

3. HALLAZGOS CLAVE DE LA EXPLORACION (para no reinventar nada)
------------------------------------------------------------------------

- ROLES = Django Groups, no un campo propio. Patron reutilizable:
  accounts/mixins.py -> GroupRequiredMixin (group_required = [...],
  con bypass automatico para superusuario). Se usara igual que en
  inventario/views.py (LoginRequiredMixin + GroupRequiredMixin).

- LOGIN Y CONTRASEÑA CADUCADA YA RESUELTOS: accounts/views.py ->
  CustomLoginView ya redirige a profile_password_change con mensaje de
  advertencia cuando profile.create_by_adr=True. Como todo vive en el
  mismo proyecto/BD, mantencion solo necesita LoginRequiredMixin normal
  (LOGIN_URL='login' ya es global). Django respeta el parametro "next"
  automaticamente, asi que tras loguearse el usuario vuelve a la pagina
  de mantencion que pedia. No se requiere ningun login propio nuevo.

- AUDITORIA GRATIS AL MOVER EQUIPOS: inventario/signals.py (evento
  pre_save sobre Activo) ya registra en AuditoriaActivo cualquier
  cambio de campo, incluido "ubicacion", usando
  adr.middleware.get_current_user(). Si mantencion actualiza
  activo.ubicacion y llama a activo.save(), el "enroque" de sala queda
  auditado sin escribir codigo adicional.

- PROCESAMIENTO DE IMAGENES YA EXISTE: common/utils.py ->
  procesar_imagen_en_memoria + common/mixins.py ->
  ImageProcessingFormMixin (resize, fuerza JPEG, quita transparencia,
  limites de 25 megapixeles / 5000px / 25MB). Se reutiliza tal cual
  para las fotos de evidencia. Para video no hay nada hoy: se agregaran
  validaciones nuevas y equivalentes (extension/tamaño) SIN
  transcodificar.

- REPORTES POR CORREO: patron productivo en
  inventario/management/commands/enviar_reporte_semanal.py (arma
  contexto, renderiza un template HTML, EmailMultiAlternatives,
  settings.EMAIL_RECIPIENTS). Se replicara para el boton manual de
  mantencion (sin el cron/GitHub Action, segun lo decidido).

- EXPORTAR A EXCEL: patron en
  inventario/views.py -> DescargarExcelFiltradoView (openpyxl, estilos
  con PatternFill/Font). Se reutiliza el mismo estilo para el boton
  "enviar reporte por excel" del modulo de revision.

- CRUD DE UBICACION YA EXISTE en inventario (UbicacionForm,
  CrearUbicacionView / EditarUbicacionView), pero EDIFICIO Y PISO NO
  TIENEN CRUD fuera del admin de Django (inventario/admin.py solo los
  expone via EdificioAdmin / PisoInline). Ese es el hueco real que pide
  el usuario ("mover salas entre edificios").

- MEDIA / ALMACENAMIENTO: STORAGES ya cambia automaticamente entre
  FileSystemStorage (local) y MediaCloudinaryStorage (produccion) segun
  core/settings/local.py y production.py. Basta con definir upload_to=
  con rutas nuevas, sin tocar configuracion.

- EL SIDEBAR ACTUAL ES POR HOVER (static/js/sidebar.js, mouseenter /
  mouseleave), no sirve para movil tactil. El navbar nuevo de
  mantencion usara un toggle por click/tap (mejor para el "uso por
  celular" que pide el brief).

- NO EXISTE MODO OSCURO en ningun lado del proyecto hoy: sera 100%
  nuevo, y solo dentro del layout propio de mantencion.

4. DISEÑO DE DATOS (app mantencion)
------------------------------------------------------------------------

Todas las relaciones (FK) usan on_delete=PROTECT donde aplica, y NINGUN
modelo tiene vista de borrado (requisito "el dato nunca se elimina"):
solo estados/flags que permiten pausar o marcar sin destruir historia.

4.1 EquipoMantenible
    El "roster" de que activos entran a mantencion mensual. Resuelve el
    punto "se agregan equipos que YA estan inventariados" sin tocar
    inventario.Activo.
    - activo: OneToOneField('inventario.Activo', on_delete=PROTECT)
    - tipo: choices PROYECTOR / IMPRESORA (explicito, no se infiere del
      nombre de Categoria para evitar fragilidad de strings)
    - activo_en_revision: BooleanField(default=True) -> pausar sin
      borrar
    - agregado_por: FK User (null), fecha_agregado: auto_now_add

4.2 CicloRevision
    Un registro por mes.
    - anio, mes, fecha_generado (auto_now_add)
    - generado_por: FK User (null = generado por el comando programado)
    - unique_together = (anio, mes)

4.3 RevisionEquipo
    Una fila por (ciclo, equipo), creada en estado "pendiente" por el
    comando mensual.
    - ciclo: FK CicloRevision
    - equipo: FK EquipoMantenible
    - estado: choices PENDIENTE / OK / NOVEDAD
    - ubicacion_en_revision: FK inventario.Ubicacion (snapshot de donde
      estaba el equipo al generarse el ciclo, asi el listado "por
      edificio y sala" no se reordena a mitad de mes si alguien lo
      mueve)
    - revisado_por: FK User (null), fecha_revision (null)
    - comentario: texto (obligatorio a nivel de formulario si
      estado=NOVEDAD)
    - unique_together = (ciclo, equipo)

4.4 EvidenciaRevision
    De 1 a N fotos/videos por revision.
    - revision: FK RevisionEquipo (related_name='evidencias')
    - archivo: FileField(upload_to='mantencion/evidencias/%Y/%m/')
    - tipo_archivo: choices FOTO / VIDEO (derivado de la extension al
      guardar)
    - subido_por: FK User, subido_en: auto_now_add

COMANDO MENSUAL (dia 1, imitando reporte_semanal.yml): por cada
EquipoMantenible con activo_en_revision=True cuyo activo no este
is_deleted ni en estado "De Baja", crea/asegura el CicloRevision del
año/mes y una fila RevisionEquipo en PENDIENTE con la ubicacion actual
del activo. Es idempotente (get_or_create), asi que tambien puede
llamarse manualmente sin duplicar filas.

5. VISTAS Y NAVEGACION
------------------------------------------------------------------------

Navbar retractil propio (templates/mantencion/base_mantencion.html):

1. Home (HomeMantencionView, TemplateView): ultima fecha de revision
   por tipo, conteo pendientes/OK/novedad del mes en curso, ultimas
   novedades.

2. Lista de impresoras / Lista de proyectores (ListView sobre
   EquipoMantenible filtrado por tipo, con select_related hasta
   activo->catalogo->marca y activo->ubicacion->piso->edificio).

3. Revision mensual -> submenu:
   - Revision de proyectores / impresoras: ListView agrupado por
     edificio/sala de las RevisionEquipo del ciclo actual (crea el
     ciclo del mes si por algun motivo el comando no corrio aun,
     como respaldo defensivo, sin reemplazar el cron).
     Botones disponibles:
       * OK (envio simple, AJAX opcional)
       * Novedad + evidencia (formulario con comentario + input de
         archivo con accept="image/*,video/*" capture, para abrir la
         camara directo en el celular)
       * Enroque (formulario pequeño para reasignar activo.ubicacion,
         reutilizando inventario.forms.UbicacionForm o un ModelForm
         ad-hoc sobre Activo.ubicacion)
       * "Enviar reporte" (genera Excel via openpyxl y/o correo HTML
         manual, ambos restringidos por permiso)

4. Cerrar sesion: reutiliza la url "logout" ya existente (sin
   duplicar).

SOLO PARA EL GRUPO ADR (mismo GroupRequiredMixin,
group_required=['ADR']):
   - Alta/baja (soft) de equipos en el roster (EquipoMantenible),
     eligiendo entre los Activo de categoria Proyector/Impresora que
     aun no esten en el roster.
   - CRUD de Edificio y Piso (el hueco real hoy): vistas nuevas dentro
     de mantencion que operan sobre los modelos de inventario (mismo
     patron cross-app que ya usa inventario/views.py al importar
     "from adr.models import Prestamo").
   - Para mover una Ubicacion de piso/edificio: se reutiliza
     inventario.forms.UbicacionForm dentro de una vista propia de
     mantencion (mismo navbar, sin salir del modulo ni duplicar la
     logica de validacion).

6. SEGURIDAD (OWASP / buenas practicas)
------------------------------------------------------------------------

- Toda vista con LoginRequiredMixin + GroupRequiredMixin, sin vistas
  publicas.
- ModelForm con fields=[...] explicitos (nunca __all__), igual que en
  el resto del proyecto.
- revisado_por / subido_por / agregado_por siempre se asignan desde
  request.user en la vista, nunca desde datos enviados por el cliente.
- Validacion de evidencia: las imagenes reutilizan
  validar_extension_imagen + procesar_imagen_en_memoria (limites ya
  existentes). Para video se añade un validador nuevo en
  common/validators.py (extension .mp4 + tamaño maximo, ej.
  MAX_VIDEO_SIZE_MB nuevo en common/utils.py, mismo estilo que
  MAX_UPLOAD_SIZE_MB).
- Rate limiting basico en los POST de "marcar OK" / "subir evidencia":
  mismo mecanismo por cache que ya usa el login (django.core.cache,
  sin agregar dependencias nuevas) para limitar envios por
  usuario/minuto.
- Nada se hardcodea: cualquier parametro nuevo (ej. MAX_VIDEO_SIZE_MB,
  destinatarios del reporte) sigue el patron config(...) de
  python-decouple / settings.EMAIL_RECIPIENTS ya existente. Jamas
  credenciales fuera del .env.
- Comentarios pedagogicos en el codigo nuevo (docstrings cortos
  explicando el "por que", igual que en inventario/signals.py), sin
  caer en bloques largos de comentarios.

7. FRONTEND
------------------------------------------------------------------------

- templates/mantencion/base_mantencion.html propio: Tailwind via CDN
  (Play CDN, igual que templates/base.html) con
  tailwind.config = { darkMode: 'class', theme: { extend: { colors:
  {...} } } } definido antes del script cdn.tailwindcss.com, para la
  paleta institucional (rojo/blanco/negro) y soporte de la variante
  "dark:".
- Switch de modo oscuro en el navbar: alterna la clase "dark" en
  <html> y persiste la preferencia en localStorage (JS nuevo, sin
  librerias externas).
- Navbar retractil con toggle por click/tap (no por hover) para que
  funcione en movil: JS nuevo y pequeño
  (static/js/mantencion_navbar.js).
- Iconos FontAwesome (ya cargado globalmente via CDN en base.html; se
  reincluye en base_mantencion.html porque el layout es independiente).
- Captura de foto/video nativa via
  <input type="file" accept="image/*,video/*" capture> - sin JS de
  camara personalizado.
